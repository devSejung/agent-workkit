# 화면이 있는 과제의 UI/UX

**읽는 때:** 화면·폼·대시보드·사용자 상호작용을 만들거나 수정할 때만. API·CLI·데이터 과제에 화면을 추가하라는 지침이 아니다. 관련 없는 전체 디자인 시스템을 만들 필요도 없다.

## 먼저 사용자 흐름

1. 누가 무엇을 끝내야 하는지, 시작 입력과 성공 결과를 한 문장으로 잡는다. 문서·기존 화면에서 답을 찾고, 결과를 바꾸는 불확실성만 질문한다.
2. 핵심 행동 → 결과 확인 → 필요할 때 수정·재시도 흐름을 정한다. 화면 수나 장식을 늘리기 전에 이 흐름이 실제로 이어지게 한다.
3. 기존 스타일·컴포넌트·아이콘·디자인 토큰을 먼저 사용한다. 새 부품이 필요하면 [재사용 판단](reuse.md)에 따라 실제 동작·접근성·의존성·라이선스를 확인한다. 이미 모달·폼·표의 키보드 동작과 예외를 잘 처리한 공개 구현이 도움이 될 수 있다. 특정 라이브러리를 선설치하지 않는다.

## 기능에 맞는 시각적 완성도

- 기존 제품이 있으면 일관성을 유지한다. 없다면 제목·본문·보조 정보의 크기, 간격, 색, 버튼 상태에 작은 공통 규칙을 정한다. 핵심 행동과 결과가 먼저 눈에 들어오게 한다.
- 업무 화면이면 읽고 비교하고 입력하는 흐름을 우선한다. 홍보 페이지의 큰 장식이나 무관한 카드·차트를 자동으로 붙이지 않는다. 제공된 디자인 요구가 있으면 그 요구를 따른다.
- 실제 콘텐츠와 긴 문자열에서도 정렬·줄바꿈·여백이 유지되는지 본다. 정보가 많으면 의미 있게 묶고, 수치에는 필요한 단위와 맥락을 붙인다.
- 버튼·링크는 설명한 행동을 실제로 수행해야 한다. 샘플 데이터가 필요하면 표시하고, 구현하지 않은 기능을 작동하는 것처럼 꾸미지 않는다.

## 빠뜨리기 쉬운 상태와 접근성

현재 흐름에 해당하는 항목만 확인한다. 별도 기능을 만들기 위한 목록으로 쓰지 않는다.

| 항목 | 확인할 내용 |
| --- | --- |
| 로딩·진행 | 처리 중임을 알 수 있고, 중복 요청을 어떻게 처리할지 정해져 있는가 |
| 빈 결과 | 처음 사용할 때와 검색 결과가 없을 때를 필요한 만큼 구분하고 다음 행동을 안내하는가 |
| 오류·복구 | 무엇을 고쳐야 하는지 알려주고 입력 보존·재시도가 필요한 곳에서 가능한가 |
| 성공 | 사용자가 완료와 결과를 확인할 수 있는가 |
| 폼·조작 | 입력에 연결된 이름/레이블이 있고, 버튼·링크의 역할이 맞으며 키보드와 포커스로 사용할 수 있는가 |
| 가독성 | 글자·대비·정보 순서가 읽기 쉽고, 상태를 색만으로 전달하지 않는가 |
| 화면 크기 | 요구된 기기·화면 크기에서 잘림·겹침·불필요한 가로 스크롤 없이 핵심 행동이 가능한가 |

목표 기기가 불명확하면 현재 제공 화면을 기준으로 하고, 웹 과제에서 작은 화면 지원이 중요한지 판단해 확인 범위를 정한다. 모든 기기·모든 접근성 기준을 검증했다고 과장하지 않는다.

## 허용된 방법으로 실제 확인

1. 기존 실행 방법으로 띄우고 핵심 입력 → 행동 → 예상 결과를 확인한다. 관련된 실패·빈 상태와 목표 화면 크기도 확인한다.
2. **브라우저 자동화의 해당 도구·방식이 공식적으로 허용되고 실행 가능하면 적극 활용한다.** 기존 테스트를 우선하고, 실제 사용 결과를 검증한다. 클릭 명령 실행이나 스크린샷 생성만으로 성공 처리하지 않는다. [환경 문서의 조건 분기](../docs/environment.md)를 따른다.
3. 자동화를 사용할 수 없으면 가능한 로컬 검사와 허용된 수동 확인을 조합한다. 로컬 이미지 입력이 가능하면 실제 화면을 읽고 수정에 활용한다. 관찰하지 않은 상호작용을 이미지 하나로 통과 처리하지 않는다.
4. 실행한 환경·화면 크기·입력·행동·기대·실제 결과를 [작업 기록](../templates/work-notes.md)의 실행 증거에 짧게 남긴다. 화면·로그는 과제 환경 안에만 둔다. 미확인 상태는 미검증으로 남긴다.

시간이 부족하면 핵심 흐름의 단절, 읽을 수 없는 내용, 입력·복구 불가, 화면 잘림부터 고친다. 그다음 일관성과 시각적 정돈을 다듬는다. UI 코드를 생성했다는 사실은 사용성과 화면 품질의 검증을 대신하지 않는다.
