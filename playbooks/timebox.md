# 제한 시간 안에 작동하는 결과 만들기

**읽는 때:** 마감이 있는 과제, 계획·설치가 길어지는 작업, 요구가 계속 추가되는 상황. 기본 세팅만 요청받았다면 구현을 시작하지 않는다.

## 시작할 때 정할 것

실제 마감 또는 남은 시간, 필수 결과, 가장 먼저 막힐 연결 하나를 확인한다. 모르는 시간을 추정해 시작 시각처럼 기록하지 않는다. 시간은 질문·탐색·구현뿐 아니라 실행·제출 점검에도 남긴다.

아래는 순서의 기준이며 고정 시간표가 아니다. 과제에 맞춰 **첫 전체 흐름의 확인 시점과 최종 점검 시작 시점**을 잡는다. 예를 들어 남은 시간의 앞쪽 1/3 안에 작은 전체 흐름을 확인하고 마지막 1/5는 검증·제출에 남길 수 있다. 이미 시간이 부족하면 필수 요구부터 더 좁힌다.

초기 파악에서는 [요구 파악](understand.md)에 따라 핵심 목적·결정·데이터 근거를 짚고, 빠진 업무 조건을 찾을 첫 질문을 앞당긴다. 첫 전체 흐름 시점까지 분석만 해도 된다는 뜻이 아니다. 질문은 근거가 생기는 즉시 제시하고, 답을 기다리는 동안 실행 경로를 확인한다. 설정 문제가 질문 준비까지 붙잡지 않도록 읽을 수 있는 자료로 먼저 진행한다.

| 단계 | 끝났다고 볼 실제 증거 |
| --- | --- |
| 첫 실행 | 기존 실행 방법으로 시작하고 필요한 의존 대상에 작은 요청이 도착함 |
| 작은 전체 흐름 | 입력 하나가 실제 처리·필요한 저장을 거쳐 필수 결과로 이어짐. 웹이면 핵심 화면에서도 확인 |
| 요구 반영 | 중요한 업무 규칙과 실패 상태를 작은 단위로 추가하고 각각 재검증 |
| 최종 점검 | 필수 결과·실제 규모·실행 방법·제출 파일·남은 한계를 대조 |

## 질문과 구현을 함께 진행

- 답이 없으면 틀릴 가능성이 큰 결정만 먼저 묻는다. 답과 무관한 실행·데이터 읽기·기존 코드 탐색은 진행한다. 작은 변경에 전체 스펙 승인을 기다리지 않는다.
- 초기 실행에서 버전·필수 환경값의 존재·DB 연결·마이그레이션·API 경계·실제 포트 중 필요한 것만 확인한다. 비밀값은 출력하지 않는다. 기존 서비스가 있으면 재사용하고 임의로 새 스택을 추가하지 않는다.
- UI와 백엔드를 따로 완성한 뒤 처음 연결하지 않는다. 웹 과제면 간단한 입력과 실제 응답을 먼저 연결한다. 임시 데이터·모의 응답은 표시하고 실제 처리 성공과 구분한다.
- 새 요구는 `필수 계약 / 확인된 핵심 업무 규칙 / 추가 편의`로 분류해 영향과 비용을 판단한다. 모든 아이디어를 현재 작업에 넣지 않는다. 추가 형식·시각화·외부 연동은 필수 흐름과 검증 시간을 확보한 뒤 선택한다.
- 첫 실행·첫 전체 흐름·중요 규칙 추가 같은 전환점과 예상 밖 지연·새 막힘·최종 점검 시점 도달 때 남은 시간과 범위를 다시 본다. 부족하면 추가 기능을 보류하고 정확성·제출 가능한 상태를 우선한다. 자동 반복 계획이나 잦은 전체 재조사는 하지 않는다.

## CLI에서 상태를 잃지 않기

중요한 전환점에 `완료 / 지금 하는 일 / 막힌 점 / 다음 행동`을 짧게 보여준다. 웹 서버가 있으면 실제 실행 명령·작업 경로·포트·로그 위치·자신이 띄운 프로세스 식별자를 과제 환경에 남긴다. 프로세스를 여러 개 무작정 다시 띄우거나 다른 작업의 서버를 종료하지 않는다.

대화가 길어지면 [빈 작업 기록](../templates/work-notes.md)에 현재 목표·확인된 규칙·실행 상태·다음 행동만 갱신한다. 재개 시 이를 먼저 읽고 오래된 실행 성공을 그대로 믿지 않는다. 포크·복구·파일 읽기는 [CLI 빠른 사용](../docs/cli-cheatsheet.md)을 참고한다.

같은 실행 실패에 진전이 없으면 [디버깅](debug.md)의 중단·대안 기준을 적용한다. 마감이 가까워졌다는 이유로 실제 실패나 미검증을 성공으로 바꾸지 않는다.
