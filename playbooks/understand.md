# 요구를 작업으로 바꾸기

**읽는 때:** 새 과제, 중요한 요구 변경, 목표나 완료 기준이 모호할 때. 작은 수정에 관련 없는 전체 저장소 조사부터 반복하지 않는다.

1. 공식 지시와 관련 README·AGENTS.md, 진입점·설정·데이터 예·기존 검증을 읽는다. 기존 변경이 있으면 먼저 구분하고 보존한다.
2. 필수 결과를 관찰 가능한 문장으로 바꾼다. “검색 기능”보다 “어떤 입력에 어떤 결과를 보여야 하는가”가 유용하다. 출처 위치를 붙이고 **명시된 요구 / 확인된 답 / 가정 / 제안**을 분리한다.
3. 사용 주체, 실제 업무, 대표 입력·출력, 실패했을 때의 처리, 제출물을 확인한다. **제공된 업무 담당자·페르소나·메신저 질문 창구가 있는지도 확인한다.** README에 모든 운영 규칙이 적혀 있다고 가정하지 않는다. 아래 질문 중 설계를 바꾸는 것부터 묻는다.

| 불확실성 | 질문의 예 | 바뀌는 결정 |
| --- | --- | --- |
| 업무의 목적 | 누가 어떤 순간에 쓰고, 어떤 결과를 얻어야 하나요? | 핵심 흐름과 화면·인터페이스 |
| 성공 조건 | 대표 입력과 기대 결과를 하나 확인할 수 있나요? | 수용 기준과 검증 데이터 |
| 예외와 우선순위 | 데이터가 없거나 잘못됐을 때 어떻게 처리하나요? 반드시 끝내야 할 범위는 어디까지인가요? | 예외 처리와 작업 순서 |
| 데이터·운영 제약 | 입력 형식·크기·갱신 방식, 저장·네트워크 제한은 무엇인가요? | 기존 구현의 적합성 |
| 제출 조건 | 어떤 파일과 실행 방법으로 확인하나요? | 패키징과 최종 확인 |

질문을 많이 만드는 것 자체가 목표가 아니다. 이미 문서에 답이 있으면 먼저 읽는다. 답변자가 없는 경우 답을 꾸미지 말고 영향이 작은 가정은 표시해 진행한다. 제출 형식이나 허용 범위를 좌우하는 문제는 보류하고 독립 작업을 먼저 한다.

4. 핵심 사용자 흐름 하나와 가장 먼저 실행할 작은 변경을 고른다. 외부 구현을 보기 전에 필수 범위를 잡아 과도한 기능을 따라가지 않게 한다.
5. 시간이 큰 과제는 구현뿐 아니라 탐색·실행·제출 확인에 쓸 여유도 확보한다. 대화나 계획만 늘어나면 작동하는 작은 결과를 먼저 확인한다.

## 업무 담당자에게 질문하기

처음에는 현재 흐름과 최근의 실제 예외를 묻고, 답에 따라 다음 질문을 고른다. 정답을 유도하거나 과거 과제의 규칙을 이번 사실처럼 제시하지 않는다.

| 알아낼 것 | 질문의 출발점 | 답에서 구체화할 것 |
| --- | --- | --- |
| 업무 결과 | 이 결과를 누가 받아서 다음에 어떤 일을 하나요? | 사용자·시점·입력·산출물·후속 업무 |
| 반복되는 문제 | 최근에 수작업이나 문의가 많이 생겼던 경우 하나를 알려주세요. | 발생 조건·영향·현재 해결 방법 |
| 다른 경우 | 평소 절차가 맞지 않는 날짜·사용자 집단·상황이 있나요? | 적용 대상·주기·예외·우선순위 |
| 포기·실패 기준 | 어떤 결과면 사용하지 않거나 다시 처리하나요? | 측정 항목·수치·단위·경계값·비교 기준 |
| 자원·충돌 | 모두 만족시킬 수 없을 때 무엇부터 지켜야 하나요? | 강제 제약·선호·비용·결정권자 |
| 전달·관리 | 결과를 어떤 형식으로 확인·전달·수정하나요? | 필수 출력과 편의 기능의 구분 |

“보통”, “제한 없음”, “가까운”, “빠른” 같은 말은 그 결정에 필요한 범위에서 구체화한다. 답변자가 모르는 값은 미확인으로 남긴다. 질문을 던졌다는 사실을 답을 얻었다는 기록으로 바꾸지 않는다.

메신저를 AI가 직접 조작할 수 없으면 **사용자가 보낼 질문 몇 개와 답에 따라 바뀌는 결정**을 대화에 짧게 보여준다. 제공된 허용 창구로 사용자가 직접 묻고, 답은 허용된 과제 환경 안에서만 다룬다. 이를 위해 Computer Use나 외부 AI를 도입하지 않는다. 답을 기다리는 동안 기존 실행 확인·데이터 형식 조사 같은 독립 작업은 진행한다.

답을 받으면 **답의 출처 → 업무 규칙 → 구현 위치 → 검증 사례**로 연결한다. 수치·주기·예외가 생겼다면 경계와 반례를 한 번 확인한다. 추가 답이 중요한 결정을 더 바꾸지 않으면 이번 질문을 마치고 구현한다. 충돌이 발견되면 해당 쟁점만 다시 묻는다.

## 필수 요구와 추가 가치를 구분

- 공식 제출·허용 조건과 README의 필수 계약을 먼저 보존한다. 업무 담당자의 선호나 추가 아이디어가 이를 자동으로 대체하지 않는다. 충돌하면 확인할 지점을 표시한다.
- 실제 확인된 규칙이 핵심 결과의 정확성을 바꾸면 필요한 최소 범위에 포함한다. 다른 사용자 집단이나 시점에도 무조건 일반화하지 않는다.
- 편의 기능은 효과와 구현·검증 비용을 비교해 `지금 / 다음 / 보류`로 둔다. 새로운 형식·화면·외부 연동은 필수 흐름이 실행된 뒤 검토한다.
- 자원에 명시적 상한이 없다는 답이 비용·운영 부담도 없다는 뜻인지는 따로 구분한다. 없는 상한을 임의로 만들지도 않는다. 선택·배정 문제가 핵심이면 [의사결정 모델](decision-model.md)을 읽는다.

실행 순서와 탐색 종료 시점은 [제한 시간 작업](timebox.md)을 따른다. 긴 스펙 완성을 첫 실행의 선행 조건으로 삼지 않는다.

**남길 것:** 필수 요구·근거·검증 방법, 중요한 질문과 실제 답 또는 미답, 다음 작은 작업. [빈 양식](../templates/work-notes.md) 중 필요한 칸만 사용한다.
