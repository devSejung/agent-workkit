# 요구를 작업으로 바꾸기

**읽는 때:** 새 과제, 중요한 요구 변경, 목표나 완료 기준이 모호할 때. 작은 수정에 관련 없는 전체 저장소 조사부터 반복하지 않는다.

이전 과제의 조건을 이번 사실로 옮기지 않는다. 이번 업무·사용자·데이터·규모·산출물·기술 선택은 이번 자료에서 다시 확인한다. 익숙한 지식과 구현도 현재 요구에 맞는지 확인한 뒤 재사용한다. 특정 문제 유형을 전제하거나 확인하지 않은 조건을 사실로 다루지 않는다.

## 빠른 초기 파악

README와 데이터에서 **과제의 핵심 목적·결정을 잡고, 문서에 없는 중요 업무 조건을 찾아낼 질문**을 빠르게 만든다. 여기서 숨은 조건은 결과의 유효성·실제 사용을 바꾸지만 문서와 데이터만으로는 알 수 없는 업무 사실·예외·우선순위다. README 요약을 첫 결과로 끝내지 말고, 핵심 결정에 어떤 조건이 빠져 있는지까지 짚는다. 질문할 근거가 생기는 즉시 제시하고 세부 조사는 이어간다.

| 순서 | 지금 확인할 것 | 멈추고 다음으로 갈 기준 |
| --- | --- | --- |
| README·지침 | 사용자·업무 목적, 실제로 내려야 할 결정, 필수 입력/출력, 완료·제출 조건, 허용 범위, 제공된 질문 창구 | 핵심 목적·결정과 이를 잘못되게 만들 미확인 조건을 지목할 수 있음 |
| 관련 데이터 | 파일/테이블과 한 행의 의미, 키·연결 관계, 규모, 필수 필드, 단위·시간·상태 값 | 최소 입력이 어디에 있는지와 모르는 의미·부족한 정보를 구분할 수 있음 |
| 조건 후보·첫 질문 | 문서에 없는 운영 예외, 데이터 의미의 모호함, 실제 사용·후속 업무의 빈틈 | 답에 따라 달라질 구현·검증을 붙인 우선 질문 몇 개가 준비됨 |
| 답 반영·첫 실행 | 확인된 규칙의 적용 대상과 검증 사례, 답과 무관한 최소 실행 | 중요한 조건은 확인 또는 미확인으로 기록하고 작은 흐름을 실행하기 시작함 |

첫 질문 전에 전체 코드 읽기·데이터 전수 정제·전체 스펙·기술 스택 비교·오픈소스 탐색을 끝내려 하지 않는다. 관련 파일부터 좁히고 깊은 조사는 구현에 필요한 때 한다. 창구가 없거나 답이 늦으면 미확인을 표시하고 독립 작업을 진행한다.

### 데이터를 빨리 읽는 범위

- README에 적힌 데이터 목록과 실제 파일·스키마를 대조한다. 사용 가능한 기존 도구로 필드와 작은 표본부터 읽는다. 헤더·스키마만 본 사실과 실제 값까지 확인한 사실을 구분한다.
- 핵심 데이터의 식별자·연결 키·입출력 대응, 필요한 필드의 존재와 대표 값, 누락·중복·연결 실패의 징후를 확인한다. 초기에는 관련 열과 작은 표본이면 충분하다. 표본에 문제가 없다고 전체 데이터가 깨끗하다고 하지 않는다.
- 규모를 싸게 셀 수 있으면 세고, 비싸면 관찰 범위·추정·미확인을 구분한다. 큰 파일·바이너리 전체를 대화에 출력하거나 원격 DB를 무제한 조회하지 않는다. 민감한 원문 값 대신 필요한 구조와 집계만 보여준다.
- 상태 코드·날짜·단위처럼 **형식은 읽어도 업무 의미가 불명확한 값**을 질문 후보로 만든다. 데이터에 필드가 있다는 이유만으로 사용 규칙을 추측해 확정하지 않는다. 필요한 데이터가 없으면 무엇이 없고 어떤 기능이 영향을 받는지 밝힌다.

### 조건 후보를 질문으로 바꾸기

핵심 결정마다 **목적에서 거꾸로 필요한 조건을 찾고, README대로 구현할 때 무심코 두게 되는 가정에 반례를 만든다.** 입력→처리→결과→실제 사용까지 따라가며 “어떤 경우에는 이 결과를 못 쓰는가?”를 생각한다. 데이터에 이상이 없어도 업무 예외는 있을 수 있다. 아래는 현재 과제의 빈틈을 찾는 관점이며 일괄 질문 목록이 아니다.

- **일반 흐름의 예외:** 어떤 대상·시점·상태에서는 같은 처리가 맞지 않을 수 있는가?
- **데이터와 현실의 차이:** 기록이 누락·지연·중복되거나 상태 의미를 잘못 읽으면 무엇이 틀리는가?
- **실패·충돌:** 어떤 결과면 사용자가 다시 처리해야 하며, 동시에 지킬 수 없는 요구는 없는가?
- **후속 업무:** 누가 결과를 받아 어떤 결정을 하며, 출력만으로 실제 일을 끝낼 수 있는가?

후보마다 `핵심 결정 → 알고 있는 근거 → 무심코 두는 가정/빠진 조건 → 틀리면 생길 문제 → 담당자에게 물을 질문`을 연결한다. 근거는 문서의 표현·데이터 관찰·업무 흐름이며, 문서에 없는 가능성은 가설로 남긴다. 이전 문제의 규칙을 후보에 끼워 넣지 않는다.

우선순위는 **필수 결과를 틀리게 하거나 큰 재작업을 만드는 질문 → 핵심 사용·검증을 바꾸는 질문 → 편의 기능 질문** 순이다. 우선 3개 안팎을 짧고 독립된 질문으로 제시하고, 중요한 쟁점이 더 있으면 이어서 묻는다. 답을 유도하는 확인 질문만 나열하지 말고 최근 실제 실패·예외 사례를 묻는 열린 질문도 필요에 따라 쓴다. 상세 문서를 다 작성한 뒤 질문을 보여주지 않는다.

사용자에게는 **핵심 목적 1~2줄과 `핵심 결정 | 근거·빠진 조건/가설 | 틀리면 생길 문제 | 우선 질문` 표**, 기다리며 할 일만 먼저 보여준다. 필요한 데이터 근거를 해당 행에 붙이고 긴 자료 요약은 뒤로 미룬다.

답을 받으면 적용 대상·시점·경계·예외 중 필요한 것만 좁혀 후속 질문을 하고, 규칙마다 작은 기대 결과를 붙인다. 첫 질문 몇 개를 보냈다는 이유로 발견을 끝내지 않는다. 핵심 결정의 중요한 미확인이 해소되거나 답변 불가로 명시되면 구현을 진행하고, 실행·시연에서 새 빈틈이 나오면 다시 해당 쟁점을 묻는다. 받은 답을 요구에 반영하지 못했거나 중대한 조건이 미확인이라면 그 상태를 남긴다.

## 파악한 내용을 작업으로 바꾸기

필수 결과는 “어떤 입력에 어떤 결과를 보여야 하는가”처럼 관찰 가능한 문장으로 쓰고 출처를 붙인다. **명시된 요구 / 확인된 답 / 가정 / 제안**을 분리한다. 문서에 이미 답이 있는 질문을 반복하지 않는다. 답변자가 없으면 영향이 작은 가정은 표시해 진행하고, 제출 형식이나 허용 범위를 좌우하는 미확인은 보류한 채 독립 작업을 한다.

핵심 사용자 흐름 하나와 가장 먼저 실행할 작은 변경을 고른다. **업무 답변이 필요한 부분 / 기술적으로 조사할 부분 / 실행으로 확인할 부분**을 구분한다. 기술 지식의 빈틈은 [기존 구현 탐색](reuse.md)으로 좁히고, 모든 불확실성을 사용자 질문이나 긴 스펙으로 해결하려 하지 않는다.

## 업무 담당자에게 질문하기

처음에는 현재 흐름과 최근의 실제 예외를 묻고, 답에 따라 다음 질문을 고른다. 정답을 유도하거나 과거 과제의 규칙을 이번 사실처럼 제시하지 않는다.

| 알아낼 것 | 질문의 출발점 | 답에서 구체화할 것 |
| --- | --- | --- |
| 업무 결과 | 이 결과를 누가 받아서 다음에 어떤 일을 하나요? | 사용자·시점·입력·산출물·후속 업무 |
| 반복되는 문제 | 최근에 수작업이나 문의가 많이 생겼던 경우 하나를 알려주세요. | 발생 조건·영향·현재 해결 방법 |
| 다른 경우 | 평소 절차가 맞지 않는 날짜·사용자 집단·상황이 있나요? | 적용 대상·주기·예외·우선순위 |
| 포기·실패 기준 | 어떤 결과면 사용하지 않거나 다시 처리하나요? | 측정 항목·수치·단위·경계값·비교 기준 |
| 자원·충돌 | 모두 만족시킬 수 없을 때 무엇부터 지켜야 하나요? | 강제 제약·선호·비용·결정권자 |
| 전달·관리 | 결과를 어떤 형식으로 확인·전달·수정하나요? | 필수 출력과 편의 기능의 구분 |

“보통”, “제한 없음”, “가까운”, “빠른” 같은 말은 그 결정에 필요한 범위에서 구체화한다. 답변자가 모르는 값은 미확인으로 남긴다. 질문을 던졌다는 사실을 답을 얻었다는 기록으로 바꾸지 않는다.

메신저를 AI가 직접 조작할 수 없으면 **사용자가 보낼 질문 몇 개와 답에 따라 바뀌는 결정**을 대화에 짧게 보여준다. 제공된 허용 창구로 사용자가 직접 묻고, 답은 허용된 과제 환경 안에서만 다룬다. 이를 위해 Computer Use나 외부 AI를 도입하지 않는다. 답을 기다리는 동안 기존 실행 확인·데이터 형식 조사 같은 독립 작업은 진행한다.

답을 받으면 **답의 출처 → 업무 규칙 → 구현 위치 → 검증 사례**로 연결한다. 수치·주기·예외가 생겼다면 경계와 반례를 한 번 확인한다. 질문과 답이 실제 규칙·작업에 반영됐는지 확인하고, 충돌이 발견되면 해당 쟁점을 다시 묻는다.

## 필수 요구와 추가 가치를 구분

- 공식 제출·허용 조건과 README의 필수 계약을 먼저 보존한다. 업무 담당자의 선호나 추가 아이디어가 이를 자동으로 대체하지 않는다. 충돌하면 확인할 지점을 표시한다.
- 실제 확인된 규칙이 핵심 결과의 정확성을 바꾸면 필요한 최소 범위에 포함한다. 다른 사용자 집단이나 시점에도 무조건 일반화하지 않는다.
- 편의 기능은 효과와 구현·검증 비용을 비교해 `지금 / 다음 / 보류`로 둔다. 새로운 형식·화면·외부 연동은 필수 흐름이 실행된 뒤 검토한다.

실행 순서와 탐색 종료 시점은 [제한 시간 작업](timebox.md)을 따른다. 긴 스펙 완성을 첫 실행의 선행 조건으로 삼지 않는다.

**남길 것:** 필수 요구·근거·검증 방법, 중요한 질문과 실제 답 또는 미답, 다음 작은 작업. [빈 양식](../templates/work-notes.md) 중 필요한 칸만 사용한다.
