# 작은 변경을 끝까지 실행하기

**읽는 때:** 요구와 재사용 방향이 정해져 실제 변경을 시작할 때.

1. 관련 파일, 기존 변경, 설치된 런타임, 프로젝트에 정의된 실행·검증 명령을 확인한다. 새 프레임워크를 선택하기 전에 현재 구조로 가능한지 판단한다.
   과제 작업 요청을 받았다면 요구 분석 초기에 기존 실행 경로도 작은 요청으로 확인한다. 필수 실행 의존성 문제를 마지막에 발견하지 않게 한다. [제한 시간 작업](timebox.md)에 따라 첫 전체 흐름을 먼저 연결한다.
2. “이 입력이 들어오면 이 결과가 나온다”로 확인 가능한 최소 단위를 고른다. 변경 파일·선택 이유·검증 방법을 짧게 알린다. 작은 작업에 별도 장문 계획은 필요 없다.
   화면·폼·사용자 상호작용이 있는 변경이면 [UI/UX](ui-ux.md)에서 필요한 흐름과 상태를 먼저 확인한다.
3. 요구에 필요한 코드만 바꾼다. 관련 없는 재정리·포맷 변경·의존성 갱신은 섞지 않는다. 제공 README·AGENTS.md·설정을 도구함 파일로 교체하지 않는다. 기능상 기존 설정 수정이 꼭 필요하면 차이를 설명하고 최소 수정한다.
4. 기존 테스트·실행 방식으로 영향을 받는 동작을 검증한다. 새 테스트는 중요한 분기나 회귀를 잡는 데 필요한 만큼만 만든다. 입력·출력·오류 처리를 확인하고, 단순 문서 수정에 의미 없는 테스트를 만들지 않는다.
5. 결과를 읽고 다음 조각으로 넘어간다. 실패하면 [디버깅](debug.md)을, 완료 직전에는 [완료 점검](finish.md)을 읽는다.

## 로컬 Git으로 변경 관리

- 변경 전에 저장소 루트와 `git status`, 관련 diff를 읽고 원래 있던 변경을 구분한다. 기존 Git 저장소가 있으면 그 이력을 사용한다. 없다면 제공 지침에서 허용하는 경우에만 과제 폴더에 로컬 저장소를 초기화한다. 도구함과 과제의 저장소를 혼동하지 않는다.
- 작고 설명 가능한 변경을 검증한 뒤, 자신이 만든 파일·부분만 명시적으로 stage하고 staged diff를 확인해 로컬 커밋한다. 사용자 변경·기록·비밀값·도구함 전체를 무심코 `git add .`로 포함하지 않는다. 커밋 메시지는 실제 변경을 설명하고 검사 통과를 꾸며내지 않는다.
- 커밋 ID와 실제 검증 범위를 과제 환경 안의 기록에 남긴다. 실행하지 못한 중간 작업을 보존할 필요가 있으면 미검증 상태를 명시하고 완료 커밋처럼 보고하지 않는다.
- 작성자 설정·권한·Git 부재로 커밋이 막히면 그 사실을 기록하고 diff로 변경을 보존한다. 전역 설정·remote·hook을 임의로 바꾸거나 Git을 무조건 설치하지 않는다. 필요한 로컬 설정은 제공 환경의 지침과 사용자가 확인한 값에 따른다.
- 되돌리기 전 diff·커밋 범위를 읽고 자신의 변경만 대상으로 삼는다. 기존 사용자 작업을 지우는 `reset --hard`, `clean` 등을 자동 실행하지 않는다. 제출 직전 미커밋 변경도 점검한다.
- 로컬 커밋은 외부 전송이 아니다. **사전체험·본시험의 모든 push·원격 쓰기는 금지**하며, 연결 테스트나 `--dry-run`도 하지 않는다.

외부 부품은 필요한 경계부터 붙이고 출처·라이선스·버전을 남긴다. 제공 환경에서 실행할 수 없는 통합은 성공으로 보고하지 않는다. 기존 파일의 삭제·대규모 교체 등 되돌리기 어려운 변경은 영향과 보존 방법을 먼저 확인한다.

내장 병렬 작업은 제공 환경의 지원·허용이 확인되고 독립 작업이 실제로 있을 때만 고려한다. 파일 소유 범위와 결과 검증 책임을 정한다. 기능이 없으면 순차 진행하며 외부 에이전트나 추가 서비스를 설치하지 않는다.
