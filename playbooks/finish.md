# 완료를 증거와 대조하기

**읽는 때:** 작은 작업 완료 보고 또는 최종 제출 직전. 검증 범위는 변경 영향과 필수 요구에 맞춘다.

1. 최신 요구·확인된 답·제출 안내를 다시 대조한다. 필수 요구마다 변경 위치와 실제 검증 증거를 연결한다. 구현 여부와 동작 검증 여부를 구분한다.
2. 프로젝트가 요구하는 검사와 영향을 받는 실제 실행을 수행한다. 단위 테스트 통과, 빌드 성공, 서버 시작은 각각 다른 증거다. 사용 흐름까지 확인했는지 별도로 본다.
3. 명령·디렉터리·입력·기대값·실제 출력·종료 코드를 읽는다. 아직 실행 중인 프로세스, 중단·시간 초과, 비어 있는 출력은 성공 근거가 아니다. 장기 실행 서비스는 시작 여부뿐 아니라 실제 요청·응답 등 확인한 관찰을 남긴다.
4. 검증 뒤 관련 코드를 바꿨다면 영향을 받는 검사를 다시 한다. 오래된 결과를 최종 상태의 증거로 재사용하지 않는다. 검사 통과 뒤 새 우려가 없으면 무의미하게 반복하지 않는다.
5. 실제 제출 경로·파일명·형식·실행 방법을 확인한다. Git을 쓰면 최종 status/diff와 로컬 커밋을 확인하되, 커밋 자체를 검증 증거로 취급하지 않는다. 변경 목록에서 임시 로그·개인 기록·키·불필요한 의존성·외부 원본 전체가 섞이지 않았는지 본다. 도구함이나 개인 작업 기록은 요구하지 않는 한 제출물에 포함하지 않는다. 제공 파일은 임의로 지우지 않는다.
6. 실제 선택 이유와 한계를 사용자가 설명할 수 있게 짧게 정리한다. 후속 서술형 답안은 작성하지 않는다. 그 단계에서는 AI와 복사·붙여넣기를 사용하지 않고 본인이 직접 작성한다.

| 상태 | 의미 |
| --- | --- |
| 통과 | 관찰된 결과가 해당 확인 항목의 기대와 일치함 |
| 실패 | 실행했고 기대와 다른 결과가 확인됨 |
| 미검증 | 실행하거나 관찰하지 않음; 그 이유가 있으면 기록 |
| 막힘 | 필요한 환경·권한·자료가 없어 진행할 수 없음; 전체 완료를 뜻하지 않음 |

화면이 있는 과제는 [UI/UX](ui-ux.md)에 따라 핵심 흐름·관련 상태·목표 화면 크기를 확인한다. 브라우저 자동화의 해당 도구·방식이 공식적으로 허용되고 실행 가능하면 실제 상호작용과 결과 검증에 활용한다. Computer Use 금지의 예외를 임의로 만들지 않는다. 미허용·미확인·실행 불가이면 로컬 검사와 허용된 사람의 수동 확인으로 가능한 범위를 확인한다. 관찰하지 않은 화면·상호작용은 미검증이다.

**완료 보고:** 바뀐 동작과 이유, 실제 통과/실패 항목, 미검증/막힘, 제출 파일과 실행 방법. “모두 정상” 대신 확인한 범위를 말한다. push·외부 업로드를 제출 방법으로 추정하지 않는다. 지정된 제출 절차를 따른다.
